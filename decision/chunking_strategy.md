# 청킹 전략

> 결론: **문서 구조 기반 청킹**(생활법령은 절·소제목 단위, 수첩은 Q&A 단위)에 **제목 경로 접두어**를 붙이는 방식을 채택한다.
> Part C에서는 한 번에 하나의 변수만 바꾼다. 고정 길이(A) → 구조 기반(B)으로 **경계 방식의 효과**를, 구조 기반(B) → 구조 기반 + 접두어(C)로 **제목 접두어의 효과**를 측정한다. 최종 채택안은 C다.

## 1. 선행 사례 조사

| 출처 | 핵심 결과 | 시사점 |
|---|---|---|
| Chroma, *Evaluating Chunking Strategies for Retrieval* (2024) | 청크가 아닌 **토큰 구간** 기준으로 검색을 평가. 전략에 따라 recall이 최대 9%p 차이. overlap을 줄이면 IoU(검색 토큰과 근거 토큰의 교집합 ÷ 합집합, 중복 검색 토큰은 분모에 반복 반영)가 개선됨. 800토큰·400 overlap처럼 큰 청크·큰 overlap 설정은 precision과 IoU가 비교군 중 가장 낮은 축에 속함(구체 수치는 corpus·top-k 조건마다 다름). "최적 전략은 데이터셋에 따라 다르다" | 과한 overlap은 검색 효율을 해칠 수 있다. 우리 데이터로 직접 비교해야 한다 |
| NVIDIA, *Finding the Best Chunking Strategy* (2025) | 해당 실험의 5개 데이터셋에서 **페이지 단위 청킹**이 평균 정확도 0.648로 가장 높았고, **섹션 단위보다도 높았다**. 사실형 질문은 256–512토큰, 분석형 질문은 더 큰 청크가 유리 | 구조 경계가 항상 낫다는 근거는 아니다. 다만 질문 유형에 따라 적정 크기가 다르다는 점과, 결국 데이터별 실험이 필요하다는 점을 보여준다 |
| Qu et al., *Is Semantic Chunking Worth the Computational Cost?* (2024) | semantic chunking은 계산 비용 대비 일관된 우위가 확인되지 않음 | 초기 버전에서 semantic chunking은 제외한다 |
| Jimeno Yepes et al., *Financial Report Chunking for Effective RAG* (2024) | 제목·표 등 **문서 구조 요소 단위 청킹**이 단락 단위보다 금융 보고서 RAG 결과를 개선. 크기 튜닝 없이 경계를 정할 수 있음 | 구조가 명확한 문서에서 구조 기반 청킹을 시도할 근거가 된다 |
| Anthropic, *Contextual Retrieval* (2024) | 청크가 원래 문맥을 잃는 문제. LLM이 생성한 문맥 설명을 청크 앞에 붙이면 top-20 검색 실패율 35% 감소(BM25 병행 시 49%) | 청크에 소속 문서·위치 정보를 붙이는 방향의 근거. 우리 방식은 LLM 생성 없이 제목 경로를 쓰므로 동일 기법이 아니라 **이 연구에서 착안한 메타데이터 보강 청킹**이다 |
| Reuter et al., *Towards Reliable Retrieval in RAG Systems for Large Legal Datasets* (2025) | 법률 문서는 문구가 비슷해 **엉뚱한 문서에서 검색되는 문제**가 심함. 문서 요약을 청크 앞에 붙이면 이 문제가 약 절반으로 줄어듦 | 두 문서가 같은 주제(재취업활동, 상병급여 등)를 다루므로 청크에 문서 출처를 명시할 필요가 있다 |

**조사에서 얻은 원칙**

1. 모든 데이터에 맞는 최적값은 없다. 우리 문서 구조를 근거로 가설을 세우고, 평가로 검증한다.
2. 청크에는 소속 문서와 위치 정보를 붙인다.
3. 과한 overlap과 semantic chunking은 초기 버전에서 쓰지 않는다.

## 3. 채택 전략: 구조 기반 청킹

### 공통 규칙

- **content_type**: `prose`(본문), `qa`, `table`, `notice`(서식 하단 안내문), `form`(빈 서식). `form`은 인덱싱에서 제외하고, `notice`는 정규화한 텍스트가 같으면 하나만 남긴다.
- **크기**: 1,500자는 분할 여부를 판단하는 soft limit다. 최종적으로는 임베딩 모델 tokenizer 기준의 **hard limit**(모델 선정 후 확정)로 검증하고, 넘으면 문단 경계에서 나눈다.
- **짧은 조각 병합**: 300자 미만 조각은 **같은 최하위 절, 같은 1단계 소제목, 같은 content_type 안에서만** 인접 조각과 합친다. Q&A 경계, 표 경계, 1단계 소제목 경계는 넘지 않는다. 합친 결과가 soft limit를 넘거나 합칠 대상이 없으면 짧은 채로 둔다.
  - 같은 1단계 소제목 아래의 2단계 소제목끼리는 합칠 수 있다. 2단계까지 막으면 100자 안팎의 조각이 많이 생겼다(구현 중 확인).
  - 절 도입부(절 제목, 출처 표기처럼 소제목이 없는 짧은 조각)는 바로 뒤 조각과 합친다.
  - 제목만 있는 단위(절 제목, 소제목 줄)는 항상 뒤따르는 내용과 같은 청크에 둔다.
- **overlap**: 0%.

### 생활법령

1. 최하위 절(`x.y.z`)을 기본 단위로 한다.
2. soft limit를 넘으면 소제목(들여쓰기로 판별) 경계에서 나누고, 그래도 길면 문단 경계에서 나눈다.
3. `※` 주석은 앞 문단과 같은 청크에 둔다.
4. 표는 아래 규칙으로 직렬화해 별도 `table` 청크로 만든다.

### 취업드림수첩

1. **Q&A 한 쌍을 한 청크**로 한다. 질문 문장이 실제 사용자 질문과 비슷해 검색에 유리하다.
2. soft limit를 넘는 항목(10번)은 하위 항목 경계에서 나누고, 각 조각 앞에 원래 질문을 다시 붙인다.
3. 그 밖의 섹션은 번호 붙은 소제목 단위로 나눈다.
4. PDF 3장 오른쪽(5쪽)의 재취업활동 기준 표는 `table` 청크로 만든다. 수첩의 표는 괘선이 없어 셀 단위 추출이 불가능하므로 **줄 단위 텍스트를 그대로** 쓰고 수동 검수한다(생활법령 표만 셀 단위로 직렬화).

### 표 직렬화

표 제목, 단위, 행·열 머리글, 주석을 함께 보존한다. **머리글은 원문 표현을 그대로 쓴다.** "1년 이상 3년 미만"처럼 경계 조건(이상·미만)이 답을 좌우하므로 줄여 쓰지 않는다.

```
표 제목: 소정급여일수 (「고용보험법」 제50조제1항 및 별표 1)
단위: 일
열(피보험기간): 1년 미만 | 1년 이상 3년 미만 | 3년 이상 5년 미만 | 5년 이상 10년 미만 | 10년 이상
행(이직일 현재 연령) 50세 미만: 120 | 150 | 180 | 210 | 240
행(이직일 현재 연령) 50세 이상 및 장애인: 120 | 180 | 210 | 240 | 270
```

- 표는 soft limit의 예외로 둔다(쪼개지 않는다).
- 표 영역은 좌표 기반 추출 결과를 규칙으로 직렬화하고, **원문과 대조해 수동 검수**한다. 표 수가 적어서 검수 비용이 작다.
- 직렬화 텍스트는 검색용 표현일 뿐이다. citation은 원문 쪽을 가리키므로 원문을 변경하지 않는다.

### 제목 경로 접두어

임베딩하는 텍스트 앞에 다음 형식의 접두어를 붙인다.

```
[생활법령 실업급여 | 2026-08-31 기준] 구직급여 > 구직급여 수급 > 구직급여 수급액 > 기초일액의 상·하한
```

Contextual Retrieval의 문맥 보강 아이디어를 LLM 호출 없이 적용한 **메타데이터 보강 청킹**이다. 문서에 이미 제목 계층이 있으므로 그것을 쓴다.

### 청크 메타데이터

| 필드 | 설명 |
|---|---|
| `chunk_id` | 청크 고유 ID |
| `doc_id` | `easylaw_unemployment_benefit` 또는 `work24_employment_dream_booklet` |
| `parent_section_id` | 소속 최하위 절(또는 Q&A 번호) |
| `section_path` | 제목 경로 |
| `content_type` | `prose` / `qa` / `table` / `notice` |
| `pdf_page_start`, `pdf_page_end` | PDF 장 번호 범위 (디버깅용) |
| `printed_page_start`, `printed_page_end` | 인쇄 쪽 번호 범위 (citation용). 생활법령은 PDF 쪽과 같고, 수첩은 책자 쪽 번호 |
| `char_start`, `char_end` | canonical text 내 본문 위치(접두어 제외). Gold 근거 구간과의 대조용 |
| `token_count` | 임베딩 tokenizer 기준 토큰 수 (임베딩 모델 선정 후 추가. 현재는 `n_chars`: 공백 제외 글자 수) |
| `cited_laws` | 본문에서 정규식으로 추출한 인용 조문 목록 |
| `as_of` | 문서 기준일 |

## 4. 실험 설계

### 조건

| 조건 | 경계 | 제목 접두어 | overlap | 비교 |
|---|---|---|---|---|
| **A (Baseline)** | 고정 토큰 길이 | 없음 | 0% | 기준점 |
| **B** | 구조 기반 | 없음 | 0% | A → B: **경계 방식의 효과** |
| **C (채택안)** | 구조 기반 | 있음 | 0% | B → C: **제목 접두어의 효과** |

- A의 청크 길이는 B의 **접두어를 제외한 본문 평균 토큰 수**로 맞춘다. 크기가 다르면 차이가 경계 때문인지 크기 때문인지 구분할 수 없다.
- A에는 접두어를 붙이지 않는다. 고정 길이 청크는 절 경계를 넘을 수 있어서, 어떤 제목을 붙여도 청크 일부에는 맞지 않는 제목이 붙기 때문이다.
- 전처리(머리말·쪽 번호 제거, 서식 제외, 안내문 중복 제거, 표 직렬화)는 세 조건 모두 같다. 즉 세 조건은 **같은 canonical text**(아래 참고)를 서로 다르게 자를 뿐이다.

### 가설

- **H1 (A → B)**: 구조 기반 경계로 바꾸면 Evidence Recall@k와 Citation 지표가 오른다. 특히 절차형·Q&A형 질문에서 크게 오를 것으로 예상한다.
  - 반대 가능성: 여러 절을 이어야 하는 추론형 질문에서는 차이가 작거나, 청크가 잘게 나뉘어 오히려 떨어질 수 있다. 그래서 결과를 **질문 유형별로 나눠서** 본다.
- **H2 (B → C)**: 제목 경로 접두어를 붙이면 Recall@k가 오르고, 특히 두 문서가 같은 주제를 다루는 질문(재취업활동, 상병급여 등)에서 **엉뚱한 문서의 청크가 검색되는 비율**이 줄어든다.

### Canonical text

- 문서별로 전처리를 마친 뒤, **접두어를 붙이기 전** 텍스트를 하나로 이어 붙인 것을 canonical text로 저장한다. 표는 직렬화된 형태로 들어간다.
- 모든 청크의 `char_start`, `char_end`와 Gold 근거 구간은 이 canonical text 기준 좌표다.
- 수첩 10번처럼 분할 후 앞에 다시 붙인 질문 문장은 canonical text에 없는 텍스트이므로 좌표 계산에서 제외한다(청크 좌표는 본문 구간만 가리킨다).

### Gold 근거 정의 (청킹과 무관)

Gold 근거를 청크 ID로 라벨링하면 조건마다 청크가 달라서 같은 Gold Set으로 비교할 수 없다. 문장 포함 여부로 판정해도, 고정 길이 청크가 근거 문장 중간에서 잘리면 관련 청크 두 개를 모두 검색해도 실패로 판정된다. 그래서 근거를 **canonical text의 문자 구간**으로 정의한다.

- 형식: `(doc_id, printed_page 범위, char_start, char_end, 근거 문장)`
- 작성: 사람이 `근거 문장`을 고르면, 스크립트가 canonical text에서 문자열을 찾아 `char_start/end`를 계산한다. 찾지 못하거나 여러 곳에서 찾으면 사람이 직접 지정한다. 문자열 일치는 이 좌표 생성을 검증하는 보조 수단으로만 쓴다.
- 판정: 검색된 top-k 청크들의 구간 합집합이 Gold 구간을 덮는 비율(**coverage**)을 계산한다. coverage가 **0.8 이상**이면 그 근거를 회수한 것으로 본다. 임계값에 따라 결론이 바뀌는지 0.5, 1.0에서도 함께 확인한다.
- 검수: 사람은 `근거 문장`을 보고 판단한다.
- Chroma 연구가 청크가 아닌 토큰 구간 기준으로 평가한 것과 같은 원리다.

### 지표

**검색 지표**

| 지표 | 정의 |
|---|---|
| **Evidence Hit@k** | 필요 근거 중 **하나 이상**을 top-k로 회수했는가 |
| **Evidence Recall@k** | 필요 근거 중 top-k로 회수한 근거의 **비율**. 근거가 여러 개인 추론형 질문에서 Hit@k와 구분된다 |
| **Evidence Coverage@k** | Gold 구간 전체 중 top-k 청크가 덮은 문자 비율(임계값 없는 연속값) |
| **Context Precision@k** | top-k 청크 중 Gold 구간과 1자 이상 겹치는 청크의 비율 |

**Citation 지표**

인용 단위는 `(doc_id, printed_page)`이며, Gold 근거의 문서가 같고 쪽 범위 안에 들면 일치로 본다.

| 지표 | 정의 |
|---|---|
| **Citation Precision** | 답변이 생성한 인용 중 Gold 근거와 일치하는 비율. 인용이 하나도 없으면 0 |
| **Citation Recall** | Gold 근거 중 답변이 하나 이상 인용한 근거의 비율 |

- 문서에 답이 없어 **거부해야 하는 질문**은 Citation 지표에서 제외하고, 거부 정확도로 따로 평가한다.
- 답변 품질 지표(정확성, 근거 충실성, 거부 정확도)는 Eval Harness 설계 문서에서 따로 정의한다.

## 5. 채택하지 않은 방식

| 방식 | 제외 이유 |
|---|---|
| Semantic chunking | 비용 대비 일관된 우위가 확인되지 않았다(Qu et al., 2024). 문서에 이미 명시적인 제목 구조가 있다 |
| LLM 생성 문맥 접두어 (Contextual Retrieval 원형) | 청크마다 LLM 호출이 필요하다. 제목 경로 접두어의 효과(B vs C)를 먼저 보고 Next Step으로 판단한다 |
| 페이지 단위 청킹 | NVIDIA 실험에서는 좋은 기본값이었지만, 생활법령은 절이 페이지를 넘나들고 수첩은 한 페이지에 Q&A가 여러 개라 경계가 의미와 맞지 않는다. 필요하면 추가 비교 조건으로 둔다 |
| 큰 overlap | 중복 정보로 검색 효율이 떨어질 수 있다(Chroma). 또 조건 간 변수 통제를 위해 모두 0%로 둔다 |

## 6. 확정 전 검수

구현 후 다음을 출력해 사람이 확인한 뒤 전략을 확정한다.

- 청크 목록(`section_path`, `content_type`, 쪽 범위, 첫 100자)과 토큰 수 분포
- 소제목 판별 오류(들여쓰기 기반 휴리스틱), 누락된 본문, 쪽 번호 매핑 오류
- 표 직렬화 결과와 원문 대조
- 중복 제거된 안내문 목록

## 7. 알려진 위험

- **표 추출**: 셀 순서가 불안정하다. 표 청크는 수동 검수하고, 표를 근거로 하는 Gold Set 질문으로 확인한다.
- **양쪽 정렬 텍스트**: 생활법령을 기본 모드로 추출하면 줄이 단어 단위로 끊긴다. 좌표 기반 추출이 필요하다.
- **소제목 판별**: 들여쓰기 기반 휴리스틱이라 오판이 생길 수 있다.
