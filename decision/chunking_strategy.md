# 청킹 전략

> 결론: **문서 구조 기반 청킹**(생활법령은 절·소제목 단위, 수첩은 Q&A 단위)에 **제목 경로 접두어**를 붙이고, **하이브리드 검색**(임베딩 + 글자 2-gram BM25를 RRF로 결합)으로 찾는다(조건 C_hybrid).
> 한 번에 변수 하나만 바꾸는 4개 조건(고정 길이 A → 구조 기반 B → 제목 접두어 C → 하이브리드 C_hybrid)을 Gold Set으로 비교해 정했다(4절). Recall@5는 0.595 → 0.623 → 0.643 → 0.691로 단계마다 올랐다.

## 1. 선행 사례 조사

| 출처 | 핵심 결과 | 시사점 |
|---|---|---|
| Chroma, *Evaluating Chunking Strategies for Retrieval* (2024) | 청크가 아닌 **토큰 구간** 기준으로 검색을 평가. 전략에 따라 recall이 최대 9%p 차이. overlap을 줄이면 IoU(검색 토큰과 근거 토큰의 교집합 ÷ 합집합, 중복 검색 토큰은 분모에 반복 반영)가 개선됨. 800토큰·400 overlap처럼 큰 청크·큰 overlap 설정은 precision과 IoU가 비교군 중 가장 낮은 축에 속함(구체 수치는 corpus·top-k 조건마다 다름). "최적 전략은 데이터셋에 따라 다르다" | 과한 overlap은 검색 효율을 해칠 수 있다. 우리 데이터로 직접 비교해야 한다 |
| NVIDIA, *Finding the Best Chunking Strategy* (2025) | 해당 실험의 5개 데이터셋에서 **페이지 단위 청킹**이 평균 정확도 0.648로 가장 높았고, **섹션 단위보다도 높았다**. 사실형 질문은 256–512토큰, 분석형 질문은 더 큰 청크가 유리 | 구조 경계가 항상 낫다는 근거는 아니다. 다만 질문 유형에 따라 적정 크기가 다르다는 점과, 결국 데이터별 실험이 필요하다는 점을 보여준다 |
| Qu et al., *Is Semantic Chunking Worth the Computational Cost?* (2024) | semantic chunking은 계산 비용 대비 일관된 우위가 확인되지 않음 | 초기 버전에서 semantic chunking은 제외한다 |
| Jimeno Yepes et al., *Financial Report Chunking for Effective RAG* (2024) | 제목·표 등 **문서 구조 요소 단위 청킹**이 단락 단위보다 금융 보고서 RAG 결과를 개선. 크기 튜닝 없이 경계를 정할 수 있음 | 구조가 명확한 문서에서 구조 기반 청킹을 시도할 근거가 된다 |
| Anthropic, *Contextual Retrieval* (2024) | 청크가 원래 문맥을 잃는 문제. LLM이 생성한 문맥 설명을 청크 앞에 붙이면 top-20 검색 실패율 35% 감소(BM25 병행 시 49%) | 청크에 소속 문서·위치 정보를 붙이는 방향의 근거. 우리 방식은 LLM 생성 없이 제목 경로를 쓰므로 동일 기법이 아니라 **이 연구에서 착안한 메타데이터 보강 청킹**이다 |
| Reuter et al., *Towards Reliable Retrieval in RAG Systems for Large Legal Datasets* (2025) | 법률 문서는 문구가 비슷해 **엉뚱한 문서에서 검색되는 문제**가 심함. 문서 요약을 청크 앞에 붙이면 이 문제가 약 절반으로 줄어듦 | 두 문서가 같은 주제(재취업활동, 상병급여 등)를 다루므로 청크에 문서 출처를 명시할 필요가 있다 |

**조사에서 얻은 원칙**

1. 모든 데이터에 맞는 최적값은 없다. 우리 문서 구조를 근거로 가설을 세우고, 평가로 검증한다.
2. 청크에는 소속 문서와 위치 정보를 붙인다.
3. 과한 overlap과 semantic chunking은 초기 버전에서 쓰지 않는다.

## 3. 채택 전략: PDF → 검수된 Markdown → 제목 기반 청킹

### 3.1 왜 Markdown을 거치는가

두 PDF는 레이아웃이 복잡하다(생활법령은 소제목이 들여쓰기로만 구분되고, 수첩은 한 장에 두 쪽·세로쓰기 표·빈 서식이 섞여 있다). PDF를 매번 자동 파싱하면 규칙이 문서 생김새에 맞춘 휴리스틱으로 가득 차고, 파싱 오류가 평가 결과에 섞여 들어간다.

그래서 **PDF는 한 번만 Markdown으로 변환하고 사람이 검수**한다. 이후 파이프라인은 Markdown만 읽는다.

```
[1회성]      PDF ──(app/utility/pdf_to_markdown: 초안 생성)──▶ Markdown ──(사람이 원문과 대조·수정)──▶ 커밋
[파이프라인] app/data/markdown/*.md ──(app/tasks/ingest: 제목 기반 청킹)──▶ 청크
```

- 문서가 버전이 고정된 PDF 2개라 1회 변환이 정당하다. PDF가 개정되면 변환과 검수를 다시 한다(한계로 기록).
- 파이프라인 규칙이 "제목에서 자르고, 길면 문단에서 자르고, 짧으면 합친다"로 단순해져 설명·검증이 쉽다.

### 3.2 Markdown 작성 규칙

- **제목**: 문서 구조를 `#` 수준으로 표현한다.
  - 생활법령: `#` 장(1.) → `##` 절(1.1.) → `###` 최하위 절(1.1.1.) → `####`·`#####` 소제목
  - 수첩: `#` 섹션 → `##` 항목(Q&A는 `## Q1.`처럼 Q로 시작) → 번호 없는 소제목 그룹이 있으면 그 아래 `###` 항목
- **쪽 표시**: `<!-- p.25 -->` 주석 줄. 다음 줄부터 25쪽이라는 뜻이고 citation 쪽 번호에 쓴다(인쇄 쪽 번호).
- **표**: Markdown 표. 병합 셀은 채우고, 행·열 머리글은 원문 표현을 그대로 쓴다("1년 이상 3년 미만"처럼 경계 조건이 답을 좌우). 계층만 있는 분류표는 `- 상위 > 하위` 목록으로 쓴다.
- **제외한 내용**: 목차, 매 쪽 머리말·쪽 번호, 수첩의 빈 서식·달력·인사말·뒤표지(중복). 서식 장의 안내 문장은 남기고, 여러 장에 반복되는 안내문과 문의처는 한 번만 둔다.
- **원문 수정 금지**: 문구는 바꾸지 않는다. 구조(제목·표·목록)만 입힌다.

초안은 `app/utility/pdf_to_markdown`이 만든다(pdfplumber로 좌표·글꼴을 읽어 제목·표를 추정). 자동 추출이 깨지는 수첩 표 3개(5쪽, 51–52쪽)는 검수 단계에서 원문 이미지를 보고 Markdown에 직접 옮겨 적었다. 초안 생성 후에도 사람이 수정할 수 있으며, **커밋된 Markdown이 원본(source of truth)**이다.

### 3.3 청킹 규칙 (`app/tasks/ingest/chunker.py`)

1. Markdown 제목으로 트리를 만든다.
2. 제목 아래 전체(하위 제목 포함)가 **1,500자(공백 제외) 이하면 하나의 청크**로 둔다. 넘으면 하위 제목으로 내려가 같은 규칙을 반복한다.
3. 하위 제목이 없는데도 길면 **문단(빈 줄 경계) 단위로 1,500자까지 채워** 나눈다. 문단과 표는 쪼개지 않는다.
4. 병합:
   - 제목만 있는 조각은 다음 조각에 붙인다.
   - 300자 미만 조각은 **같은 상위 제목 아래의 이웃 조각**과 합친다(같은 제목의 조각끼리, 상위 도입부와 첫 하위 항목, 같은 상위 제목의 형제끼리). 최상위 섹션끼리는 합치지 않는다.
   - **Q&A(Q로 시작하는 제목)는 합치지 않는다.** 한 Q&A가 길어 나뉘면 뒤쪽 조각에 질문을 `question_prefix`로 다시 붙인다.
5. overlap은 0%.

### 제목 경로 접두어

임베딩과 BM25에 넣는 텍스트 앞에 다음 형식의 접두어를 붙인다.

```
[생활법령 실업급여 | 2026-08-31 기준] 2. 구직급여 > 2.3. 구직급여 수급 > 2.3.2. 구직급여 수급액 > 기초일액의 상·하한
```

Contextual Retrieval의 문맥 보강 아이디어를 LLM 호출 없이 적용한 **메타데이터 보강 청킹**이다. 문서에 이미 제목 계층이 있으므로 그것을 쓴다.

### 청크 메타데이터

| 필드 | 설명 |
|---|---|
| `chunk_id` | 청크 고유 ID (`EL-0000`, `BK-0000`) |
| `doc_id` | `easylaw_unemployment_benefit` 또는 `work24_employment_dream_booklet` |
| `section_path` | 제목 경로 |
| `content_type` | `qa`(Q&A 제목 아래) / `prose` |
| `has_table` | 표 포함 여부 |
| `page_start`, `page_end` | 인쇄 쪽 번호 범위 (citation용) |
| `char_start`, `char_end` | canonical text 내 위치(접두어 제외). Gold 근거 구간과의 대조용 |
| `n_chars` | 공백 제외 글자 수 (임베딩 모델 선정 후 토큰 수 추가) |
| `cited_laws` | 인용 조문 목록. 항·호까지 보존하고(`고용보험법 제46조제1항제1호`), 한 법령 뒤의 여러 조문(`제45조제5항, 제46조제1항제1호`, `제2조제1항제5호·제6호`)을 모두 펼친다. 조문 없이 인용된 고시는 이름만 저장 |
| `question_prefix`, `title_prefix` | 나뉜 Q&A의 질문 재부착, 검색용 제목 경로 접두어 |
| `as_of` | 문서 기준일 |

## 4. 실험 (완료: C_hybrid + 질의 재작성 채택)

비교 조건 A, B, C의 코드와 인덱스는 채택 후 삭제했다. 비교를 다시 돌리려면 커밋 `a0bb8bc`에서 `python -m app.tasks.ingest.build && python -m app.tasks.index.build && python -m app.tasks.eval.retrieval`을 실행한다.

### 조건

| 조건 | 경계 | 제목 접두어 | 검색 | overlap | 비교 |
|---|---|---|---|---|---|
| **A (Baseline)** | 고정 길이 | 없음 | dense | 0% | 기준점 |
| **B** | 구조 기반 | 없음 | dense | 0% | A → B: **경계 방식의 효과** |
| **C (채택안)** | 구조 기반 | 있음 | dense | 0% | B → C: **제목 접두어의 효과** |
| **C_hybrid** | 구조 기반 | 있음 | dense + BM25 (RRF) | 0% | C → C_hybrid: **키워드 검색 결합의 효과** |
| **C_hybrid + 재작성 (채택안)** | 구조 기반 | 있음 | LLM 질의 재작성 → dense + BM25 (RRF) | 0% | C_hybrid → 재작성: **질의 재작성의 효과** |

- A의 청크 길이는 B 청크 본문의 **평균 크기(공백 제외 654자)**로 맞춘다. 크기가 다르면 차이가 경계 때문인지 크기 때문인지 구분할 수 없다. 처음에는 토큰 수로 맞출 계획이었지만, 청킹 전체가 공백 제외 글자 수를 기준으로 하므로 같은 단위를 쓴다. 단어 중간에서 자르지 않도록 654자에 이른 뒤 처음 나오는 공백에서 끊는다(`chunker.chunk_fixed`).
- 임베딩 입력의 제목 자리는 C만 제목 경로를 쓰고, A와 B는 `title: none`으로 둔다(`models.md`의 문서 접두어 형식).
- C_hybrid는 C와 같은 인덱스를 쓰고, BM25 순위(제목 경로 + 본문)를 dense 순위와 RRF(k=60)로 합친다. BM25는 k1=1.2, b=0.75 기본값이다. 36문항에 맞춰 파라미터를 조정하면 과적합이 되므로 조정하지 않는다.
- 재작성은 `gemini-3.8-flash`(temperature 0)가 질문을 문서 용어의 검색어 문장으로 바꾸고, 그 문장으로 dense와 BM25를 모두 검색한다. 답변은 원래 질문으로 만든다. 프롬프트는 첫 버전을 그대로 쓴다(`search.REWRITE`). 나빠진 문항을 보고 고치면 Gold Set에 과적합되기 때문이다.
- A에는 접두어를 붙이지 않는다. 고정 길이 청크는 절 경계를 넘을 수 있어서, 어떤 제목을 붙여도 청크 일부에는 맞지 않는 제목이 붙기 때문이다.
- 전처리(머리말·쪽 번호 제거, 서식 제외, 안내문 중복 제거, 표 직렬화)는 모든 조건이 같다. 즉 세 조건은 **같은 canonical text**(아래 참고)를 서로 다르게 자를 뿐이다.

### 가설

- **H1 (A → B)**: 구조 기반 경계로 바꾸면 Evidence Recall@k와 Citation 지표가 오른다. 특히 절차형·Q&A형 질문에서 크게 오를 것으로 예상한다.
  - 반대 가능성: 여러 절을 이어야 하는 추론형 질문에서는 차이가 작거나, 청크가 잘게 나뉘어 오히려 떨어질 수 있다. 그래서 결과를 **질문 유형별로 나눠서** 본다.
- **H2 (B → C)**: 제목 경로 접두어를 붙이면 Recall@k가 오르고, 특히 두 문서가 같은 주제를 다루는 질문(재취업활동, 상병급여 등)에서 **엉뚱한 문서의 청크가 검색되는 비율**이 줄어든다.
- **H3 (C → C_hybrid)**: 글자 2-gram BM25를 RRF로 결합하면 여러 근거가 필요한 질문(multi_hop)의 Recall@k가 오르고, 일반적인 내용이라 어떤 질문과도 적당히 비슷한 청크(예: 88자 절 도입 BK-0040)가 top-k를 차지하는 일이 줄어든다.
  - 근거(사전 관찰): C의 첫 평가에서 BK-0040이 36문항 중 13문항의 top-5에 들었지만 근거를 담은 적은 없었다. 임베딩 유사도만 높고 겹치는 키워드는 적은 청크라 순위 결합으로 밀려날 것으로 예상했다.
  - 토크나이저: 형태소 분석(kiwipiepy, 명사·어근·접두사)과 글자 2-gram을 같은 조건에서 비교했다. 하이브리드 Recall@5가 2-gram 0.691, 형태소 0.605로 2-gram이 나았다. 형태소 분석은 "조기재취업수당"을 "조기/재/취업/수당"으로 나눠 흔한 조각끼리 두루 맞고, 띄어쓰기가 틀린 질문에 약하다. 2-gram은 이어진 글자 조각을 보존해 정확한 용어 일치를 잡는다. 의존성도 없어 2-gram을 쓴다.

- **H4 (C_hybrid → 재작성)**: 질문을 문서 용어로 바꿔 검색하면 표현이 문서와 다른 질문(KIN-41 "군입대로 중지" ↔ 문서 "수급기간 연기")에서 근거를 찾게 되어 Recall@k가 오른다.
  - 근거(사전 관찰): C_hybrid에서 근거를 하나도 못 찾은 4문항(KIN-09, 31, 40, 41)은 모두 구어 표현과 문서 용어가 달랐다. CLI에서 "실업급여 받다가 군대 가면?"도 답변 불가로 거부됐다.

### 결과

2026-09-25, Gold Set 36문항(answerability none 제외), 모든 조건에서 임베딩 모델(`gemini-embedding-2`)과 질문 임베딩은 같다.

| 조건 | Hit@5 | Recall@5 | Coverage@5 | Recall@10 | 다른 문서 비율@5 |
|---|---|---|---|---|---|
| A 고정 길이 | 0.889 | 0.595 | 0.637 | 0.706 | 0.243 |
| B 구조 기반 | 0.917 | 0.623 | 0.662 | 0.753 | 0.383 |
| C + 제목 접두어 | 0.917 | 0.643 | 0.674 | 0.754 | 0.357 |
| C_hybrid | 0.889 | 0.691 | 0.735 | 0.792 | 0.357 |
| **C_hybrid + 재작성** | **0.972** | **0.788** | **0.826** | **0.901** | - |

| 가설 | ΔRecall@5 | 좋아진 / 나빠진 문항 | 판정 |
|---|---|---|---|
| H1 A → B | +0.028 | 10 / 7 | 약하게 지지 |
| H2 B → C | +0.020 | 4 / 1 | 약하게 지지 |
| H3 C → C_hybrid | +0.048 | 6 / 3 | 지지 |
| H4 C_hybrid → 재작성 | +0.097 | 9 / 4 | 지지 (효과가 가장 큼) |

질문 유형별 Recall@5:

| 유형 | 문항 | A | B | C | C_hybrid | + 재작성 |
|---|---|---|---|---|---|---|
| factoid | 15 | 0.689 | 0.811 | 0.833 | 0.867 | 0.956 |
| multi_hop | 13 | 0.519 | 0.488 | 0.519 | 0.612 | 0.675 |
| procedural | 7 | 0.524 | 0.512 | 0.512 | 0.512 | 0.655 |

- **H1**: 규정 하나를 찾는 질문(factoid)은 크게 올랐지만(0.69 → 0.81), 여러 근거가 필요한 질문(multi_hop)은 조금 떨어졌다. 가설의 "반대 가능성"이 관찰됐다. 절차형(procedural)에서 크게 오른다는 예측은 빗나갔다. k=1, 3에서는 B가 A보다 낮았다.
- **H2**: 다른 문서 청크 비율은 예측대로 줄었지만(0.383 → 0.357) 폭이 작고, 고정 길이 A(0.243)가 가장 낮았다. 문서 혼동에는 제목 접두어보다 경계 방식의 영향이 더 커 보인다.
- **H3**: multi_hop이 0.52 → 0.61, Recall@1이 0.29 → 0.42로 올랐다. 88자 절 도입 청크 BK-0040이 top-5에 든 문항은 13개 → 1개로 줄었다. 대신 Hit@5는 1문항 떨어졌다.
- **H4**: 근거를 못 찾던 4문항 중 3개(KIN-31, 40, 41)를 찾았다. KIN-41은 재작성이 "군 복무로 인한 수급기간 연기"를 만들어 Recall@5가 0 → 1.0이 됐다. 세 유형이 모두 올랐다. 나빠진 4문항(KIN-15, 16, 19, 38)은 재작성이 두 가지를 묻는 질문을 한쪽으로 좁히거나(KIN-19: 조기재취업수당 조건 쪽으로 쏠림, 1.00 → 0.33), 사용자가 쓴 정확한 단어가 긴 공식 문장에 묻혀 BM25에서 힘을 잃은 경우다. KIN-09(알바 소득 신고)는 여전히 실패한다.
  - **비결정성**: temperature 0에서도 실행마다 재작성 질의가 달라진다(3회 실행에서 36문항 모두 같은 문항 0개). 5회 실행한 Recall@5는 0.726~0.791(평균 0.774)로, 표의 0.788은 그중 한 번이다. 그래도 모든 실행이 C_hybrid(0.691)보다 높다.
  - **seed 지정 후 (변경)**: 이 실험 뒤 재작성·답변·Judge 호출에 seed 42를 넘기도록 바꿨다. seed 없이는 3회 실행에서 재작성 질의가 같은 문항이 0개였지만, seed 지정 후 검색 평가 3회에서는 36문항 중 35~36개가 같았고 Recall@5는 0.769~0.783이었다. 다만 한 단어 차이(KIN-39의 '고용보험' 유무)로 문항 Recall이 0.5 ↔ 1.0으로 바뀌는 경우가 남아 완전한 결정론은 아니다. 위 표는 seed 도입 전 측정값이다. 리포트에 문항별 재작성 질의를 계속 남긴다.
  - **비용**: 질문마다 LLM 호출이 1번 늘어 응답이 그만큼 느려진다.
- **임계값**: 0.5, 0.8, 1.0 어느 쪽이든 모든 조건의 Recall이 같았다. 근거 102개 중 A의 청크 경계에 걸린 것이 10개뿐이고, 일부만 덮인 3개도 0.5 미만이었다. 근거 문장(평균 100자 안팎)이 청크(650자 안팎)보다 훨씬 짧기 때문이다.
- **한계**: 36문항이라 모두 통계적으로 확정할 수준은 아니다(H3의 6 대 3은 부호 검정 p≈0.25, H4의 9 대 4는 p≈0.27). 경향으로 읽는다.

### 결론

단계마다 Recall@5가 올랐다. 청킹·검색 구조는 추가 비용이 작고 의존성도 없는 **C_hybrid**를 쓰고, 그 위에 효과가 가장 큰 **질의 재작성**을 더한다. 재작성은 LLM 호출 1번의 지연을 대가로 Recall@5를 0.097 올린다. 실행 간 변동은 seed 지정으로 크게 줄였다(위 H4 비결정성).

### Canonical text

- 검수된 Markdown에서 주석 줄(쪽 표시 등)만 뺀 텍스트다. `app/data/processed/{doc_id}.canonical.txt`로 저장한다.
- 모든 청크의 `char_start`, `char_end`와 Gold 근거 구간은 이 텍스트 기준 좌표다. 조건 A/B/C 모두 같은 canonical text를 서로 다르게 자를 뿐이다.
- 나뉜 Q&A 앞에 다시 붙이는 질문과 조건 C의 제목 접두어는 canonical text 밖의 텍스트이므로 좌표에 포함하지 않는다.

### Gold 근거 정의 (청킹과 무관)

Gold 근거를 청크 ID로 라벨링하면 조건마다 청크가 달라서 같은 Gold Set으로 비교할 수 없다. 문장 포함 여부로 판정해도, 고정 길이 청크가 근거 문장 중간에서 잘리면 관련 청크 두 개를 모두 검색해도 실패로 판정된다. 그래서 근거를 **canonical text의 문자 구간**으로 정의한다.

- 형식: `(doc_id, printed_page 범위, char_start, char_end, 근거 문장)`
- 작성: 사람이 `근거 문장`을 고르면, 스크립트가 canonical text에서 문자열을 찾아 `char_start/end`를 계산한다. 찾지 못하거나 여러 곳에서 찾으면 사람이 직접 지정한다. 문자열 일치는 이 좌표 생성을 검증하는 보조 수단으로만 쓴다.
- 판정: 검색된 top-k 청크들의 구간 합집합이 Gold 구간을 덮는 비율(**coverage**)을 계산한다. coverage가 **0.8 이상**이면 그 근거를 회수한 것으로 본다. 임계값에 따라 결론이 바뀌는지 0.5, 1.0에서도 함께 확인한다.
- 검수: 사람은 `근거 문장`을 보고 판단한다.
- Chroma 연구가 청크가 아닌 토큰 구간 기준으로 평가한 것과 같은 원리다.

### 지표

**검색 지표**

| 지표 | 정의 |
|---|---|
| **Evidence Hit@k** | 필요 근거 중 **하나 이상**을 top-k로 회수했는가 |
| **Evidence Recall@k** | 필요 근거 중 top-k로 회수한 근거의 **비율**. 근거가 여러 개인 추론형 질문에서 Hit@k와 구분된다 |
| **Evidence Coverage@k** | Gold 구간 전체 중 top-k 청크가 덮은 문자 비율(임계값 없는 연속값) |
| **Context Precision@k** | top-k 청크 중 Gold 구간과 1자 이상 겹치는 청크의 비율 |
| **다른 문서 비율@k** | 근거가 한 문서에만 있는 문항에서 top-k 중 다른 문서 청크의 비율 (H2) |

**Citation 지표**

인용 단위는 `(doc_id, printed_page)`이며, Gold 근거의 문서가 같고 쪽 범위 안에 들면 일치로 본다.

| 지표 | 정의 |
|---|---|
| **Citation Precision** | 답변이 생성한 인용 중 Gold 근거와 일치하는 비율. 인용이 하나도 없으면 0 |
| **Citation Recall** | Gold 근거 중 답변이 하나 이상 인용한 근거의 비율 |

- 문서에 답이 없어 **거부해야 하는 질문**은 Citation 지표에서 제외하고, 거부 정확도로 따로 평가한다.
- 답변 품질 지표(정확성, 근거 충실성, 거부 정확도)는 Eval Harness 설계 문서에서 따로 정의한다.

## 5. 채택하지 않은 방식

| 방식 | 제외 이유 |
|---|---|
| Semantic chunking | 비용 대비 일관된 우위가 확인되지 않았다(Qu et al., 2024). 문서에 이미 명시적인 제목 구조가 있다 |
| LLM 생성 문맥 접두어 (Contextual Retrieval 원형) | 청크마다 LLM 호출이 필요하다. 제목 경로 접두어의 효과(B vs C)를 먼저 보고 Next Step으로 판단한다 |
| 페이지 단위 청킹 | NVIDIA 실험에서는 좋은 기본값이었지만, 생활법령은 절이 페이지를 넘나들고 수첩은 한 페이지에 Q&A가 여러 개라 경계가 의미와 맞지 않는다. 필요하면 추가 비교 조건으로 둔다 |
| 큰 overlap | 중복 정보로 검색 효율이 떨어질 수 있다(Chroma). 또 조건 간 변수 통제를 위해 모두 0%로 둔다 |
| 고정 길이 청킹 (조건 A) | Recall@5 0.595로 네 조건 중 가장 낮았다(4절) |
| 제목 접두어 없는 구조 기반 (조건 B) | Recall@5 0.623. 접두어를 붙인 C보다 낮았다 |
| 임베딩만 쓰는 검색 (조건 C) | Recall@5 0.643. BM25를 결합한 C_hybrid보다 낮고, 일반적인 청크(BK-0040)가 top-k를 차지했다 |
| 원래 질문 + 재작성 질문 검색 결과를 RRF로 합침 | 스크래치 실험에서 Recall@5 0.737로 재작성만 쓸 때(0.791)보다 낮았다. 원래 질문 순위가 재작성 효과를 희석한다. 악화 문항을 줄이는 안전장치 역할은 한다 |
| 검색 실패 시에만 재작성 (답변 불가 판정 → 재작성 → 재시도) | 평소 LLM 호출이 1번이지만, 실패 판정이 LLM에 달려 검색 평가만으로 측정할 수 없다. 정답을 아는 상한선도 Recall@5 0.770으로 재작성보다 낮고, 답이 없는 질문은 호출이 3번이 되며 거부해야 할 질문에 답할 위험이 있다 |
| 재작성 프롬프트에 few-shot 예시 3개 추가 | Gold Set에 없는 주제(사망 시 미지급 급여, 이주비·광역구직활동비, 자영업자 폐업)로 만든 예시였다. 3회 평균 Recall@5 0.759로 현재 프롬프트(0.763)와 차이가 실행 간 변동보다 작았고, 비결정성도 줄지 않았다. KIN-19는 두 질문을 모두 남기게 됐지만 Recall은 그대로여서 원인이 재작성이 아니었다 |
| 문서 쪽 확장 (doc2query: 청크마다 예상 질문을 생성해 색인) | 질문할 때 추가 호출이 없지만 측정하지 않았다. 응답 지연이 문제가 되면 먼저 비교할 후보 |
| 형태소 분석 BM25 (kiwipiepy) | 하이브리드 Recall@5 0.605로 글자 2-gram(0.691)보다 낮았다. 복합 용어를 흔한 조각으로 나눠 두루 맞는다 |

## 6. 검수와 회귀 테스트

- Markdown 검수: 원문 PDF와 대조해 누락·제목 수준·표 값·쪽 표시를 확인한다. 커밋 후에는 Markdown이 원본이다.
- 청크 검수: `python -m app.tasks.ingest.build`가 만드는 `chunk_report.md`(청크 목록, 크기 분포)로 확인한다.
- 회귀 테스트(`pytest tests`): 생활법령 최하위 절 22개, 수첩 Q&A 29개, Q10은 2개 청크이며 두 번째에 질문 접두어, Q&A끼리 병합 안 됨, 1,500자 초과 청크는 쪼갤 수 없는 단일 블록뿐, 제목만 있는 청크 없음, canonical 구간 일치, 그룹 제목 경로, 쪽 범위, 소정급여일수 표 값, 분류표, 재취업활동 표의 세 수급자 유형, 문의처 1개, 조문 추출 예시.

## 7. 알려진 한계

- **1회 변환**: PDF가 개정되면 Markdown 변환·검수를 다시 해야 한다.
- **사람 검수 의존**: 검수자가 놓친 추출 오류(띄어쓰기 누락, 표 셀 오독)는 그대로 남는다. 핵심 표는 테스트로 고정했다.
- **질의 재작성**: seed를 지정했지만 제공사가 결정론을 보장하지 않아, 모델 갱신 등으로 재작성 결과가 바뀔 수 있다. 여러 가지를 함께 묻는 질문을 한쪽으로 좁히는 경우가 있다(4절 H4).
- **수첩 표의 조문**: 수첩 표는 "(제50조제1항 관련)"처럼 법령명 없이 조문만 적혀 있어 `cited_laws`가 비어 있다.
